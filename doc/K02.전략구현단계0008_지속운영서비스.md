# K02. 전략 구현 단계 0008 — 지속 운영 서비스

작성일: 2026-07-23  
범위: 시장별 반복 평가, 재진입 방지, 중지, 오류 격리, 시작 복구와 보호 감사  
검증 정책: 테스트는 작성만 했고 실행·네트워크 호출·배포는 수행하지 않았다.

## 1. 단계 목표

자율 전략 오케스트레이터를 일회성 호출이 아니라 지속 운영 가능한 주기로 감싼다.

각 주기는:

1. 시장 컨텍스트를 생성한다.
2. 신뢰 가능한 포트폴리오·위험 스냅샷을 생성한다.
3. 미보호 포지션 전역 차단 상태를 모든 종목의 `RiskSnapshot`에 주입한다.
4. 전략별 후보 스캔과 활성 포지션 재평가를 실행한다.
5. 한 전략이나 시장의 오류를 다른 전략·시장과 격리한다.

## 3. 서비스 계약

`ContinuousStrategyService`는 구체적인 시세·계좌·브로커 구현에 의존하지 않는다.

### `ContextProvider`

```text
market_context(market) -> MarketContext
portfolio_context(market) -> PortfolioContext
```

### `RecoveryHooks`

```text
reconcile_open_orders(market)
audit_unprotected_positions(market) -> ProtectionGateSignal
```

실제 네트워크 I/O는 후속 어댑터가 담당한다. 이번 구현에는 브로커나 데이터 제공자 실구현이 없다.

## 4. 시작 복구

`startup_recovery()`는 첫 주기 전에 시장별로 다음을 수행한다.

1. 미종결 managed order 대사
2. 미보호 전략 포지션 감사

한 시장의 복구 실패가 다른 시장의 복구를 막지 않는다. 다만 주문 대사나 보호 감사가 실패한 시장은 신규 위험 차단 집합에 들어간다.

복구 결과는 시장별 메시지와 `blocked_markets`로 반환된다.

## 5. 시장별 실행과 재진입 방지

시장마다 별도 `threading.Lock`을 두고 `blocking=False`로 획득한다.

동일 시장의 이전 주기가 아직 실행 중이면 새 호출은 기다리거나 중첩 실행하지 않고:

```text
status = reentry_skipped
```

를 반환한다.

KR 주기가 실행 중이어도 US 주기의 별도 lock에는 영향을 주지 않는다.

## 6. 중지

외부에서 주입 가능하고 내부 기본값도 제공하는 `threading.Event`를 사용한다.

- `stop()`이 이벤트를 설정한다.
- 시장 순회와 전략 순회 사이에 중지 여부를 확인한다.
- `run_forever()`는 `sleep`이 아니라 `Event.wait(interval)`을 사용하므로 중지 요청에 즉시 반응할 수 있다.
- 객체 생성만으로 백그라운드 스레드를 시작하지 않는다.

## 7. 오류 격리와 fail-closed

### 전략 오류

한 전략의 `run_cycle()` 예외는 해당 전략 오류로 기록하고 다음 전략을 계속 실행한다. 활성 포지션을 관리해야 하는 다른 전략을 건너뛰지 않는다.

### 시장 오류

`run_iteration()`에서 한 시장의 예외는 `market_error`로 변환하고 다음 시장을 계속 실행한다.

### 안전 스냅샷 오류

시장 또는 포트폴리오 스냅샷 생성이 실패하면 값을 추정하지 않는다.

- 해당 시장을 신규 위험 차단 상태로 설정
- 오케스트레이터를 호출하지 않음
- `safety_snapshot_blocked` 반환

따라서 불완전한 계좌·시장 값으로 신규 주문이 생성되지 않는다.

### 보호 상태

각 주기 시작에 보호 감사를 다시 수행한다.

- 미보호 수량 존재 또는 감사 오류: 시장 차단
- 정상 감사: 이전 차단 해제 가능
- 차단 결과를 모든 종목의 `RiskSnapshot.protection_global_block`에 주입
- `RiskEnvelope`가 ENTER/ADD/buy를 결정론적으로 거부
- 위험 감소 매도는 계속 허용

## 8. 후보와 포지션의 지속 평가

서비스가 호출하는 `AutonomousStrategyOrchestrator.run_cycle()`은:

- `adapter.scan()`으로 신규 후보 의도를 생성
- DB의 활성 전략 포지션을 조회
- 각 포지션에 `adapter.manage_position()` 호출

따라서 서비스의 한 주기는 시장, 신규 후보, 모든 활성 포지션을 함께 평가한다.

주기 키는:

```text
market + 평가시각 + strategy_id
```

로 구성되어 전략 결정의 멱등 키 기반이 된다.

## 9. 작성한 테스트

`tests/test_autonomy_continuous_service.py`에 다음 테스트를 작성했다.

1. 시작 시 모든 시장의 managed order 대사와 보호 감사
2. 미보호 차단 상태를 모든 trusted `RiskSnapshot`에 주입
3. 스냅샷 실패 시 전략 주기를 호출하지 않는 fail-closed
4. 한 전략 실패 뒤 다음 전략 계속 실행
5. 동일 시장 재진입 lock
6. stop event 설정 뒤 추가 시장 주기 방지

사용자 지시에 따라 테스트는 실행하지 않았다.

## 10. 후속 작업

1. `ContextProvider`의 KR/US 실제 구현
2. managed order 상태 조회·잔고 대사를 수행하는 `RecoveryHooks` 구현
3. 기존 `strategy_scheduler.py` 또는 VM 서비스 진입점에서 명시적으로 서비스 구동
4. 전략별 실행 주기와 시장 개장 시간 정책
5. 장애 백오프와 운영 상태/heartbeat 영속화
6. 다중 프로세스 환경용 DB/분산 lease 추가
7. 최종 단계에서 stop, 동시성, 재시작, 오래 걸리는 주기 장애주입 테스트 실행

현재 lock은 단일 프로세스 내 재진입을 막는다. 여러 프로세스가 동시에 서비스를 실행할 가능성이 생기면 DB lease가 추가되기 전까지 단일 인스턴스 운영을 강제해야 한다.

## 11. 단계 결과

자율 전략의 시장·후보·활성 포지션 평가를 반복 실행할 수 있는 중지 가능한 서비스 계층이 마련됐다. 시작 복구, 시장별 lock, 전략·시장 오류 격리와 안전 스냅샷 fail-closed가 명시적으로 구현됐다.

이 단계는 서비스를 실제로 시작하거나 네트워크 어댑터를 연결하지 않는다. 기존 운영 스케줄러 연결과 배포는 후속 승인 범위다.
