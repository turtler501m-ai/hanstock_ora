# 전략 구현 단계 0009: 승인·실행 파이프라인

## 목적

결정론적 리스크 승인을 받은 관리 주문을 기존 KR/US 승인 원장에 연결하고,
운영자 승인 시점에 안전 조건을 다시 확인한 뒤에만 브로커 제출 경로를
개방한다. 승인 대시보드의 일반 주문과 자율 전략 관리 주문이 식별자 없이
섞이는 것을 금지한다.

## 승인 원장 보강

공통 `ApprovalRepository`와 KR/US approvals 마이그레이션에 다음 컬럼을
추가했다.

- `managed_order_id`
- `decision_id`
- `position_id`
- `client_order_key`
- `strategy_version`
- `profile_hash`

`ApprovalRecord`, `ApprovalCreateRequest`, `ApprovalService`도 같은 필드를
끝까지 전달한다. 승인 상태 변경은 `WHERE id=? AND status='pending'` CAS를
사용할 수 있도록 `transition_pending()`을 추가했다.

## 승인 대기열 연결

`ManagedApprovalBridge.queue()`의 순서는 다음과 같다.

```text
canonical managed order 확인(risk_approved)
→ decision/position 소유권 확인
→ 기존 approvals에 전체 식별자 저장
→ managed order에 approval_id CAS 결합
→ approval_queued 전이
```

결합이나 상태 전이에 실패하면 승인 행과 관리 주문을 거절 상태로 닫아 활성
위험예약이 남은 채 실행 가능한 고아 주문이 생기지 않게 한다.

## 승인 시점 재검증

승인은 단순히 approvals 상태만 바꾸지 않는다. 다음 항목을 모두 다시 읽어
검증한다.

1. approval과 managed order의 ID, client key, decision, position, strategy 일치
2. decision과 position의 시장·종목·전략 소유권 일치
3. 전략 lifecycle이 현재도 `approved`, `live_limited`, `live` 중 하나
4. 전략 버전과 profile hash가 승인 생성 시점 및 현재 catalog와 일치
5. decision에 승인된 결정론적 risk 결과 존재
6. 신규 매수에는 활성 risk reservation 존재
7. 신규 위험에는 전역 hard-stop protection gate가 열려 있음

## 승인 직전 최신 위험 재평가

저장된 과거 `RiskDecision`은 주문 원본 무결성을 확인하는 감사 기준일 뿐,
최종 승인 근거로 단독 사용하지 않는다. `ManagedApprovalBridge`는 필수 주입된
`FreshRiskSnapshotProvider`에서 최신 authoritative `RiskSnapshot`을 가져와
decision의 원본 `intent_payload`를 `TradeIntent`로 재구성하고 최초 판단과
동일한 `RiskEnvelope`로 다시 평가한다.

Provider 호출에는 현재 주문의 활성 예약 ID를 전달하며, 반환 스냅샷의 예약
노출은 그 자기 예약만 제외해야 한다. 자기 주문을 신규 주문처럼 다시 더해
이중계산하는 것을 막되 다른 모든 pending 예약은 유지한다.

최신 평가에서 다음 중 하나라도 발생하면 주문 내용을 자동 변경하거나 수량을
확대하지 않고 승인 전체를 거절한다.

- snapshot 조회 실패
- 데이터 신선도 초과 또는 미래 시각
- 비허용 시장 국면
- 일일 손실·킬스위치·보호 전역 게이트 차단
- 현금·종목·시장·섹터·전략·유동성·계좌 위험 한도 실패
- 최신 허용 수량이 기존 요청 수량보다 작음

최신 허용 수량이 더 커도 기존 요청 수량을 그대로 유지한다. 즉 승인 단계는
주문을 확대하거나 가격·수량을 다시 작성하는 기능이 아니다.

`sell`, `REDUCE`, `EXIT`는 위험감소 경로이므로 시장 국면이나 신규 위험
한도로 막지 않는다. 대신 최신 snapshot의 전략 소유 수량을 다시 확인하고
요청 매도수량이 이를 넘으면 fail-closed로 거절한다.

재검증이 하나라도 실패하면 관리 주문은 `rejected` terminal로 전이하고
위험예약을 해제하며 승인 행도 거절한다. 보호 전역 게이트는 신규 `buy`에만
적용하므로 위험을 줄이는 매도 승인을 막지 않는다.

## 실행 조정기

`ManagedExecutionCoordinator.execute()`는 다음 세 조건을 다시 확인한다.

- approval 상태가 `approved`
- approval의 전체 canonical 링크가 관리 주문과 일치
- managed order 상태가 `approved`

그 뒤에만 approval ID를 명시해 `ManagedOrderService.submit()`을 호출한다.
상태 서비스의 `approve()`와 `submit()`도 관리 주문에 결합된 approval ID가
없거나 다르면 거부한다. 브로커 어댑터는 이어서 `submitting` CAS 상태를
확인하므로 승인 원장, 관리 주문, 브로커 격리가 한 경로로 연결된다.

실행 조정기는 검증 직후 해당 `ManagedOrderService` 인스턴스만 확인할 수 있는
일회성 내부 capability를 발급받아 `submit()`에 전달한다. approval ID만
알거나 canonical 주문 dict를 확보해도 capability가 없으면 직접 제출 호출은
거부된다.

## 거절과 만료

- 운영자 거절: approval과 managed order를 `rejected`로 종료
- 주문 유효기간 만료: approval은 `expired`, managed order는 `expired`
- 두 경우 모두 주문 상태 서비스의 terminal 정책으로 활성 예약 해제
- 일부라도 체결된 이후에는 승인 대기 상태가 아니므로 이 경로로 되돌아오지 않음

## 검증 코드

`tests/test_autonomy_approval_bridge.py`에 다음 검증을 작성했다.

- approval 원장의 전체 canonical identity 저장
- 승인 시 재검증 후 실행 조정기 제출 허용
- 보호 전역 게이트 차단 시 거절 및 예약 정리
- pending approval의 직접 실행 차단
- 최신 위험 허용수량 감소 시 원주문 불변 상태로 거절
- 최신 snapshot 조회 실패 시 fail-closed
- 최신 전략 소유수량 내 위험감소 매도 승인

기존 주문 상태 테스트도 approval ID 없이는 승인·제출할 수 없도록 갱신했다.
사용자 지시에 따라 테스트는 실행하지 않았으며 실주문과 배포도 수행하지
않았다.
