# K02 전략구현 단계 0012: DB 동시성 정적 리뷰

## 범위와 제약

- 대상: `ai_stock_repository`, 공용 `DBWrapper`, 승인 저장소/서비스, 자율 주문 대조 계층
- 관점: 스키마 초기화, 트랜잭션 경계, CAS, 멱등성, 위험 예약, 체결 귀속, 하드스톱 보호, 승인 연결
- 사용자 지시에 따라 이 단계에서는 테스트와 Python 실행을 하지 않았다.
- 배포 작업은 수행하지 않았다.

## 확인한 안전 불변식

1. 전략 포지션 활성 소유권은 `(market, account_id, symbol, strategy_id)` 부분 유니크 인덱스로 중복 생성을 막는다.
2. 전략 판단과 관리 주문은 각각 `decision_key`, `client_order_key` 유니크 제약으로 재실행을 차단한다.
3. 주문 상태 변경은 `WHERE id=? AND status=?` CAS와 같은 트랜잭션의 이벤트 기록으로 구성된다.
4. 위험 예약은 SQLite 쓰기 잠금을 먼저 획득한 뒤 계좌·시장 전체 활성 예약 합계를 검사하고 삽입한다.
5. 예약 해제는 `status='active'` 조건부 갱신이므로 반복 호출이 예산을 이중 반환하지 않는다.
6. 매도 체결은 관리 주문의 전략·시장·종목 소유권과 전략 가상 보유수량을 검사한다.
7. 하드스톱 가격은 손실 확대 방향으로 낮출 수 없고, 포지션 수량이 남아 있으면 취소할 수 없다.
8. 승인 레코드는 관리 주문·판단·포지션·클라이언트 주문 키를 보존해 실행 경로를 역추적할 수 있다.

## 발견 및 수정 사항

### 1. 체결 재전달에 의한 이중 귀속

기존 `apply_managed_fill`은 원자적으로 주문과 포지션을 갱신했지만 동일한 브로커 관측을 두 작업자가 동시에 처리하면 동일 증분이 두 번 반영될 수 있었다.

수정:

- `(order_id, fill_key)` 유니크인 `ai_managed_fills` 원장을 추가했다.
- 동일 키·동일 수량·동일 가격은 성공한 멱등 재호출로 반환한다.
- 동일 키가 다른 체결 내용을 가리키면 실패 폐쇄한다.
- 브로커 누적 체결 대조는 `broker-cumulative:{누적수량}` 키를 전달한다.
- 체결 원장, 주문 누적 체결, 전략 포지션 귀속, 주문 이벤트를 하나의 쓰기 트랜잭션에 둔다.

### 2. 체결과 보호 의도 사이의 커밋 간격

기존 경로는 매수 체결을 먼저 커밋하고 별도 호출로 보호 요청을 저장했다. 프로세스가 두 호출 사이에 종료되면 열린 포지션은 검색으로 탐지되지만 영속 보호 의도가 없는 순간이 존재했다.

수정:

- 매수 체결 시 전체 전략 보유수량을 대상으로 `pending`/`amend_pending` 보호 의도와 이벤트를 같은 트랜잭션에 기록한다.
- 손절가가 없거나 유효하지 않으면 체결의 로컬 귀속 전체를 롤백한다.
- 매도 체결 시 남은 수량에 대한 보호 정정 또는 전량 청산 후 취소 요청 상태를 같은 트랜잭션에 기록한다.
- 브로커 API 호출 자체는 DB 트랜잭션에 포함할 수 없으므로 커밋 이후 수행한다. 실패 시 영속 요청 및 전역 보호 게이트가 복구 대상으로 남는다.

### 3. SQLite 전용 쓰기 시작문

원자적 함수들이 PostgreSQL 연결에서도 `BEGIN IMMEDIATE`를 실행할 수 있었다.

수정:

- `_begin_write`를 추가해 SQLite는 `BEGIN IMMEDIATE`, PostgreSQL은 `BEGIN`을 사용한다.
- 스캔 생성, 주문 CAS, 체결, 스냅샷, 위험 예약, 보호 상태 변경, 일일 기준자산 생성의 명시적 쓰기 트랜잭션을 이 함수로 통일했다.

### 4. 승인 큐 중복과 거절 경쟁

관리 주문 승인 생성에는 영속 유니크 제약이 없어 재시도/동시 작업자가 같은 주문의 승인을 여러 개 만들 수 있었다. 거절도 선행 조회 후 무조건 갱신하여 승인 실행과 경쟁할 수 있었다.

수정:

- `managed_order_id`와 비어 있지 않은 `client_order_key`에 부분 유니크 인덱스를 추가했다.
- SQLite 승인 삽입은 충돌 시 기존 승인 ID를 반환하는 멱등 동작으로 바꿨다.
- 승인 거절은 `pending -> rejected` CAS를 사용한다. 동시에 다른 작업자가 상태를 변경하면 덮어쓰지 않는다.

### 5. 필수 안전 스키마 초기화 실패 은폐

자율 전략 테이블 초기화 실패가 경고만 남기고 애플리케이션 초기화를 계속할 수 있었다. 이 경우 위험 예약·보호 테이블이 빠진 상태로 시작할 가능성이 있었다.

수정:

- 초기화 오류 시 롤백하고 `RuntimeError`를 발생시켜 실패 폐쇄한다.

## 정적 검토 결과

- 변경 파일 대상 `git diff --check`에서 공백 오류가 발견되지 않았다.
- `ai_stock_repository`의 직접 `BEGIN IMMEDIATE` 사용은 제거되고 `_begin_write` 내부에만 남았다.
- 테스트 및 Python 구문 실행은 최종 검증 단계로 유보했다.

## 최종 검증 단계에서 필요한 항목

1. 동일 누적 체결을 병렬 대조해 포지션 수량과 실현손익이 한 번만 변하는지 검증
2. 동일 `fill_key`에 다른 수량/가격을 전달할 때 거부되는지 검증
3. 매수 체결 직후 보호 요청 행과 이벤트가 반드시 존재하는지 검증
4. 체결 트랜잭션 중 보호 생성 실패를 주입해 주문·포지션·체결 원장이 함께 롤백되는지 검증
5. 동일 관리 주문 승인 동시 생성 시 승인 ID가 하나로 수렴하는지 검증
6. 승인 실행과 거절 경쟁 시 하나의 CAS 전이만 성공하는지 검증
7. SQLite 잠금 경쟁에서 위험 예산과 현금 한도를 초과하지 않는지 검증
8. 지원 대상으로 유지할 경우 PostgreSQL에서 스키마 DDL, ID 반환, upsert 문법을 별도로 통합 검증

## 잔여 주의점

- 공용 `DBWrapper`는 SQL 자리표시자와 일부 자동증가 DDL만 PostgreSQL 형식으로 변환한다. 기존 AI 저장소의 `INSERT OR REPLACE`, `INSERT OR IGNORE`, `lastrowid` 사용은 PostgreSQL 완전 호환이 아니다. 현재 운영 DB가 SQLite라면 이번 동시성 보강은 유효하지만, PostgreSQL을 실제 지원 범위로 선언하려면 저장소 전반을 `ON CONFLICT ... RETURNING` 기반으로 별도 정리해야 한다.
- 브로커 주문 제출과 DB 커밋은 단일 원자 트랜잭션이 될 수 없다. 따라서 `submitting` 선점, 클라이언트 주문 키, `broker_unknown`, 재대조 루프가 계속 필수다.

## 후속 보강: 필수 보호 실행 통합

정적 재검토 결과 영속 보호 의도만으로는 충분하지 않았다. 실제 실행 서비스에
`ProtectionBroker`가 주입되지 않으면 매수 체결 후에도 주문이 `filled`로 끝나고
위험 예약이 해제될 수 있었다.

다음 실행 불변식을 추가했다.

1. `ManagedOrderService.submit`은 `buy` 주문에 사용 가능한 보호 브로커가 없으면
   브로커 주문 제출 전에 거부한다.
   `ManagedExecutionCoordinator`도 승인 연결을 확인한 직후 같은 조건을 검사해
   실제 실행 조립에서 우회할 수 없게 한다.
2. 매수 체결은 보호 브로커 확인 후 전체 열린 수량과 동일한 `active` 보호가
   확인되어야 성공으로 반환하고 위험 예약을 종료한다.
3. 부분 매도 체결은 남은 전체 수량으로 보호 주문이 정정되어 `active` 상태인지
   확인한다.
4. 전량 매도 체결은 보호 주문이 `canceled`, 보호수량 `0`으로 확인되어야 성공한다.
5. 보호 호출 실패 또는 불완전 확인 시 체결 자체는 브로커의 권위 있는 사실로
   유지하지만 호출은 오류로 종료한다. 따라서 reconciler/run은 해당 주문을
   정상 완료로 보고하지 않으며 복구 루프가 처리한다.
6. 기본 운영 조립은 보호 경계를 생략하지 않는다.
   - DRY_RUN/demo/paper: `PaperProtectionBroker`
   - live KIS/US: 실제 하드스톱 어댑터가 아직 없으므로
     `UnavailableProtectionBroker`를 명시적으로 주입하고 신규 매수를 차단한다.

추가한 미실행 테스트:

- 보호 브로커 미주입 매수 제출 차단
- 명시적 미지원 보호 어댑터 매수 제출 차단
- 모의 보호 브로커의 제출·조회·취소 확인
- 브로커 누적 체결 테스트 더블의 `fill_key` 전달 호환

이 후속 테스트도 사용자 지시에 따라 작성만 했으며 실행하지 않았다.
