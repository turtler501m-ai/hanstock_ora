# K02. 전략 구현 단계 0011 — 완료 전 갭 감사

작성일: 2026-07-23  
범위: 단계 0001의 요구사항 1~15 및 안전 불변조건 S-01~S-16 재검증  
검증 정책: 현재 작업 트리의 코드를 권위 증거로 정적 감사했다. 테스트·네트워크·배포는 실행하지 않았다.

## 1. 판정 기준

- `complete`: 현재 코드가 요구 계약을 직접 강제하며 알려진 우회 경로가 없음
- `weak`: 핵심 구현은 있으나 운영 조립, 기존 경로 통합, 브로커 구현 또는 최종 실행 증거가 부족
- `missing`: 요구 기능을 직접 구현한 권위 코드가 없음

테스트가 작성되어 있어도 실행되지 않았으면 광범위한 완료 증거로 사용하지 않았다.

## 2. 이번 감사에서 직접 수정한 갭

`ManagedApprovalBridge._revalidate()`는 lifecycle 평가용 객체에 `action`을 넣지 않았다. 10단계에서 lifecycle이 action-aware가 된 뒤 이 객체는 평가 중 예외를 일으켜 승인 재검증을 모두 fail-closed할 수 있었다.

이번 단계에서 주문 방향에 따라:

```text
buy  -> TradeAction.ENTER_LONG
sell -> TradeAction.EXIT
```

을 명시적으로 전달하도록 보완했다.

이로써 승인 시에도 중단 전략의 신규 매수는 차단되고, 기존 포지션의 승인된 위험 감소 매도는 계속 평가될 수 있다.

## 5. 특별 점검 결과

### 5.1 위험 감소 가용성

다음 신규 위험 차단 중에도 위험 감소는 허용된다.

- kill switch
- 일일 손실 한도
- 보호 전역 block
- lifecycle `review_required/suspended/retired`
- strategy health halt
- 전략 카탈로그 조회 오류/누락

근거:

- `RiskEnvelope.evaluate()`가 reduction을 increase 검사 전에 분기
- `StrategyLifecycleGate.evaluate()`가 action-aware 허용
- approval bridge가 주문 방향을 lifecycle action으로 전달
- 전략 소유 수량과 trusted 실제 보유량이 수량 상한

### 5.2 재시작 복구

존재:

- 미종결 managed order 목록
- 브로커 누적 체결과 로컬 누적 체결 비교
- fill delta 적용
- 불가능한 역행·초과 상태의 `broker_unknown`
- continuous 시작 시 order reconciliation hook
- 미보호 포지션 audit hook

부족:

- 실제 KR/US API callback을 concrete `RecoveryHooks`에 주입하는 운영 조립
- 다중 프로세스 lease

이번 P0 보완에서 `AutonomousRecoveryService`를 추가했다. 시작 시 managed
orders를 대사하고, 모든 open 전략 포지션에 대해 protection row 누락·failed·
partial·수량 불일치를 찾아 durable request를 재생성한다. 기존 broker stop을
조회해 일치하면 활성 상태를 복구하고, 없으면 새 보호 주문을 제출한다. 복구가
불완전하면 protection audit가 신규 위험 전역 차단을 반환한다.

또한 동일 계좌·종목의 전략 가상 잔량 합과 브로커 실제 보유 수량을 비교한다.
불일치하면 보호 주문을 재생성하지 않고 `protection_recovery_incomplete`로 신규
위험을 차단한다.

### 5.3 fallback

새 AI planner는 실패 시 후보 점수나 규칙 주문을 대신 생성하지 않는다. 모델 응답의 `fallback_used`는 반드시 표시되고 lifecycle profile에서 명시 승인되지 않으면 주문이 거부된다.

레거시 `ModelPredictor`는 규칙 점수 fallback을 유지한다. 다만 `automation_service`의 레거시 직접 브로커 실행은 비활성화되어 자율 실행 경로로 안내된다. 완전 제거 전까지 분석 결과와 실행 결과를 혼동하지 않도록 표시가 필요하다.

### 5.4 KR/US

두 시장 모두:

- canonical persisted managed order만 받음
- 동일 submit/cancel/fetch 계약
- 동일 상태 머신
- 동일 reconciliation
- market 불일치 거부

하지만 실제 API callback과 조건부 하드스톱 구현은 아직 제공되지 않는다.

### 5.5 승인

승인 레코드는 managed order, decision, position, client order key, 전략 버전·해시에 연결된다. 승인 시:

- lifecycle 재평가
- 결정론적 risk 승인 존재
- 주문 수량·가격 일치
- 승인/결정/포지션 버전·해시 일치
- buy risk reservation 존재·금액 일치
- 미보호 전역 block

를 재검증한다. 실행은 승인된 managed approval과 내부 authorization 객체가 없으면 불가능하다.

약점은 승인 대기 중 변한 가격·계좌·일손실·데이터 신선도를 새 trusted snapshot으로 다시 risk 평가하지 않는 점이다.

### 5.6 lifecycle

전략 상태, 정확한 버전·프로필 해시, fallback 승인, 건강 임계를 평가한다. 건강 중단은 상태 변경·선택 해제·이벤트를 한 트랜잭션으로 처리한다.

위험 감소 액션은 차단 상태에서도 허용된다.

### 5.7 persistence

현재 권위 원장:

- 불변 market/portfolio snapshots
- strategy decisions
- strategy virtual positions
- managed orders/events
- active risk reservations
- protection state/events
- approval links
- strategy lifecycle events

핵심 unique/CAS/`BEGIN IMMEDIATE` 제약이 존재한다. 독립 fill 테이블과 포지션 ledger가 별도로 없고 managed order event 및 position 누적 필드에 의존하는 점은 장기 감사 확장성의 약점이다.

## 6. 완료를 막는 잔여 우선순위

### P0 — 최종 검증 전 필수

1. 승인 실행 직전 최신 시장·계좌 snapshot으로 risk envelope 재평가
2. 실제 KR/US API callback과 protection adapter를 `AutonomousRecoveryService`에 조립
3. 최종 테스트 실행 및 실패 수정

### P1 — 운영 자율화 전 필수

1. KR/US 실제 보호주문 adapter
2. continuous service 운영 진입점·heartbeat·단일 인스턴스 lease
3. 실제 브로커 잔고 기반 매도 직전 상한 재검증
4. 자율 경로 외 주문이 중앙 커널을 우회하지 않도록 통합 또는 명시적 격리

### P2 — 감사 품질 강화

1. 독립 fills/position ledger
2. 주문·보호 대사 이력의 장기 보존
3. fallback 분석 결과와 실행 가능 결과 UI 분리

## 7. 완료 전 결론

새 `src/strategy/autonomy/` 경계에는 완전 거래 의도, 결정론적 수량, 전략 포지션 소유권, 원자 위험 예약, 승인 authorization, 주문 상태 머신, 재시작 대사 기반, 하드스톱 보호, 정량 시장국면, 지속 평가와 건강 자동중단이 구현되어 있다.

그러나 최초 목표 전체는 아직 완료로 판정할 수 없다.

S-08 권위 일일 주문 수 제한과 protection crash-gap 시작 복구는 이번 보완에서 구현됐다. 실제 운영 조립과 보호주문 adapter, 승인 직전 최신 snapshot 재평가, 최종 테스트 실행은 남아 있다.

따라서 현재 상태는 “자율 플랫폼 핵심 도메인과 안전 커널 구현 완료, 실제 운영 완결성과 최종 검증 미완료”로 판정한다.
