# K02. 전략 구현 단계 0006 — 하드스톱 보호

작성일: 2026-07-23  
범위: 진입 체결 직후 하드스톱 요청, 보호 수량 원장, 손절 완화·취소 금지, 미보호 전역 차단  
검증 정책: 테스트는 작성했으나 실행하지 않았다. 브로커 실호출과 배포는 수행하지 않았다.

## 1. 단계 목표

전략 소유 포지션의 진입 체결 수량이 보호되지 않은 채 방치되는 것을 탐지하고, 보호 공백이 존재하는 동안 모든 신규 위험 증가 주문을 차단할 수 있는 결정론적 신호를 제공한다.

핵심 불변조건:

1. 진입 fill이 전략 포지션에 반영된 직후 전체 open 수량에 대한 보호 요청을 먼저 영속화한다.
2. 브로커 제출 성공이 아니라 브로커가 인정한 보호 수량만 `protected_qty`가 된다.
3. `protected_qty < remaining_qty`이면 미보호 수량이 존재한다.
4. 장기 포지션의 하드스톱은 가격을 올릴 수만 있고 내릴 수 없다.
5. 전략 소유 open 수량이 1주라도 있으면 하드스톱을 취소할 수 없다.
6. 보호 상태 조회 실패도 안전하다고 추정하지 않고 신규 위험을 차단한다.

## 3. 보호 상태 원장

### 3.1 `ai_position_protections`

전략 포지션별 하나의 현재 보호 상태를 저장한다.

- `position_id`: `ai_strategy_positions` 소유 포지션
- `market`, `account_id`, `symbol`, `strategy_id`, `side`
- `required_qty`: 현재 보호해야 하는 전체 open 수량
- `protected_qty`: 브로커가 실제 인정한 보호 수량
- `initial_stop_price`: 최초 하드스톱
- `current_stop_price`: 현재 요청/활성 하드스톱
- `status`: `pending`, `amend_pending`, `partial`, `active`, `failed`, `canceled`
- `broker_order_id`, `last_error`
- 생성·갱신·활성·완료 시각

`position_id`는 유일하므로 같은 포지션에 독립적인 하드스톱 레코드가 중복 생성되지 않는다.

### 3.2 `ai_position_protection_events`

요청·변경·브로커 활성·실패·취소를 추가 전용 이벤트로 기록한다.

이벤트에는 상태 전후, 필요/보호 수량, 손절가, 브로커 주문 ID, payload, 사유가 포함된다. 현재 상태 행만으로는 알 수 없는 보호 공백의 발생 원인을 추적할 수 있다.

## 4. 브로커 독립 보호 서비스

`HardStopProtectionService`는 실제 증권사 구현을 알지 못한다. 다음 `ProtectionBroker` Protocol만 사용한다.

```text
submit_hard_stop(request) -> ProtectionAck
amend_hard_stop(request) -> ProtectionAck
cancel_hard_stop(request) -> ProtectionAck
```

이번 단계에는 KIS, LS 또는 미국 주식 브로커 구현을 추가하지 않았다. 따라서 실주문 경로는 열리지 않는다.

### 4.1 진입 체결 보호

`protect_entry_fill()` 순서:

1. `filled_qty`와 전략 포지션의 현재 open 수량 검증
2. 전체 `remaining_qty`를 대상으로 DB 보호 요청 영속화
3. 기존 브로커 보호 주문이 없으면 제출, 있으면 수량 변경 요청
4. 브로커 ACK의 주문 ID, 보호 수량, 손절가 기록
5. 전량 보호이면 `active`, 일부만 보호하면 `partial`
6. 예외·거절이면 `failed` 이벤트 및 경보

새 fill만 보호하는 것이 아니라 포지션 전체 open 수량을 목표로 한다. 추가매수 체결 뒤에도 기존 수량과 신규 수량을 합한 전체 수량이 보호 기준이다.

### 4.2 손절 강화만 허용

`tighten_stop()`과 DB `request_position_protection()`이 모두 새 가격을 검사한다.

장기 포지션에서:

```text
new_stop >= current_stop
```

만 허용된다. 낮은 손절가는 “손실 확대 방향”으로 판정해 브로커 호출 전에 거부한다.

브로커 ACK가 요청한 손절가보다 낮은 가격을 반환하는 경우도 활성화하지 않는다.

### 4.3 취소 금지

`cancel_after_flat()`은 전략 포지션의 `remaining_qty == 0`일 때만 브로커 취소를 요청한다. DB `cancel_position_protection()`도 동일 조건을 트랜잭션 안에서 다시 검사한다.

따라서 서비스 계층 검사를 우회해 저장소를 직접 호출해도 open 포지션의 보호를 취소할 수 없다.

## 5. 미보호 포지션과 전역 차단

`list_unprotected_strategy_positions()`는 다음 조건을 만족하는 모든 장기 전략 포지션을 반환한다.

- 포지션 상태가 `open` 또는 `exit_pending`
- `remaining_qty > 0`
- 보호 행이 없음
- 또는 보호 상태가 활성/변경중 상태가 아님
- 또는 `protected_qty < remaining_qty`

`HardStopProtectionService.global_gate_signal()`은 결과가 하나라도 있으면:

```text
block_new_risk = true
reason = "unprotected_open_quantity"
```

를 반환하고 포지션별 경보 메시지를 생성한다.

보호 DB 조회가 예외를 일으키면:

```text
block_new_risk = true
reason = "protection_state_unavailable"
```

를 반환한다. 보호 여부를 확인할 수 없는 상태는 fail-closed다.

`amend_pending` 상태는 기존 브로커 주문의 `protected_qty`까지만 보호된 것으로 계산한다. 추가매수로 `required_qty`가 늘었는데 변경 체결이 끝나지 않았다면 차이 수량 때문에 계속 차단된다.

## 6. 작성한 테스트

`tests/test_autonomy_protection.py`에 다음 검증을 작성했다.

1. 진입 fill 후 전체 open 수량의 보호 요청 및 활성화
2. 부분 보호 시 전역 신규위험 차단과 경보
3. 보호 행 누락 시 전역 차단
4. 장기 하드스톱 하향 변경 거부 및 브로커 미호출
5. open 포지션 보호 취소 거부 및 브로커 미호출
6. 브로커 거절의 실패 상태·이벤트 영속화와 전역 차단

사용자 지시에 따라 테스트는 실행하지 않았다.

## 7. 아직 필요한 통합

`ManagedOrderService.apply_fill()`과 결정론적 `RiskEnvelope` 연결을 추가했다.

- 매수 fill 원장 반영 직후 전체 open 수량 보호 요청을 영속화한다.
- `ProtectionBroker`가 주입되면 동일 흐름에서 제출·활성화한다.
- 브로커가 없으면 `pending` 상태가 유지되어 전역 차단된다.
- 브로커 오류/거절은 `failed`로 남고 전역 차단된다.
- fill 자체는 이미 확정된 권위 이벤트이므로 보호 오류 때문에 되돌리거나 재처리하지 않는다. 반환 결과의 `protection_error`로 복구 작업에 전달한다.
- 매도 fill 후 잔량이 있으면 보호 필요 수량 변경을 영속화하고, flat이면 취소 요청을 `cancel_pending`으로 영속화한다.
- 보호 주문 수량이 포지션 잔량보다 많거나 적은 경우 모두 불일치로 판정한다.
- `RiskSnapshot.protection_global_block`을 신뢰 입력으로 추가하고, `ENTER_LONG/ADD/buy` 평가에서 `all_open_positions_protected` 검사를 강제한다.
- 위험 감소 매도는 이 전역 차단으로 막지 않는다.

후속 필수 작업:

1. 보호 요청을 만들기 전까지 매수 fill 처리 사이에 프로세스가 종료된 경우 재시작 복구 작업
2. 포트폴리오 `RiskSnapshot` 생성기가 `global_gate_signal()`을 조회해 `protection_global_block`에 넣도록 운영 경로 연결
3. 브로커별 조건부/스톱 주문 어댑터 구현
4. 하드스톱 실제 체결을 전략 포지션과 주문·체결 원장에 귀속
5. 브로커 주문 조회를 통한 보호 주문 존재·가격·수량 대사
6. 보호 주문을 지원하지 않는 시장의 서버 감시형 대체 실행기와 장애 정책
7. 장애가 지속될 때 위험 감소 시장가 청산 정책의 운영자 승인

## 8. 단계 결과

하드스톱을 단순 계획 필드가 아니라 전략 포지션 수량과 연결된 독립 보호 원장으로 승격했다. 보호 요청은 브로커 호출 전에 지속되고, 부분 보호·실패·누락은 모두 신규 위험 전역 차단 신호가 된다. 장기 손절 완화와 open 상태 취소는 서비스 및 DB 양쪽에서 금지된다.

목표 완성을 위해서는 다음 통합 단계에서 이 차단 신호를 중앙 위험 커널의 필수 입력으로 연결하고, 체결 직후 호출·재시작 복구·브로커 대사를 구현해야 한다.
