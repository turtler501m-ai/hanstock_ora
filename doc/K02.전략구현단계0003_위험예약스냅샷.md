# K02. 전략 구현 단계 0003 — 위험 예약과 불변 스냅샷

작성일: 2026-07-23

검증 정책: 테스트 코드는 작성했으나 사용자 지시에 따라 이 단계에서는 실행하지 않았다. 배포하지 않았다.

## 1. 단계 목표

동시에 실행되는 전략과 작업자가 동일한 현금 및 위험예산을 각자 가용하다고 판단하는 문제를 차단한다. 또한 AI와 결정론적 위험 엔진이 실제로 사용한 시장·계좌 입력을 나중에 재현할 수 있도록 불변 스냅샷으로 저장한다.

이번 단계가 직접 강화하는 감사 불변조건은 다음과 같다.

- S-01: 모든 주문의 중앙 결정론적 위험 통제 기반
- S-04: 실제 현금과 포트폴리오 노출 확인
- S-10: 중복 주문 및 이중 예약 방지
- 요구사항 10: 멱등 처리 기반
- 요구사항 11: 판단 입력부터 주문까지 감사 사슬

## 3. 불변 시장 스냅샷

`ai_market_snapshots`를 추가했다.

주요 필드:

- `snapshot_key`: 호출자가 생성하는 전역 멱등 키
- `market`: 저장 가능한 `KR` 또는 `US`
- `source`: 데이터 원천
- `data_as_of`: 시장 데이터 기준 시각
- `regime`: 당시 시장 국면
- `payload`: 정렬된 canonical JSON
- `payload_hash`: SHA-256
- `created_at`: 저장 시각

`create_market_snapshot()`은 동일 키와 완전히 같은 시장·원천·기준시각·국면·payload가 다시 들어오면 기존 ID를 반환한다. 동일 키가 다른 내용을 가리키면 거부한다.

스냅샷은 생성·조회·목록 API만 제공하며 수정/삭제 API를 의도적으로 제공하지 않는다. 감사 입력은 생성 후 바꿀 수 없다는 계약이다.

## 4. 불변 포트폴리오 스냅샷

`ai_portfolio_snapshots`를 추가했다.

주요 필드:

- `snapshot_key`, `account_id`, `market`
- `source`, `data_as_of`
- `cash`, `total_eval`, `stock_eval`
- 전체 보유 및 미체결 정보를 담을 수 있는 `payload`
- canonical payload의 SHA-256
- `created_at`

현금·총평가액·주식평가액은 유한한 0 이상의 값만 허용한다. NaN, 무한대, 음수는 저장 전에 거부한다.

동일 키의 재요청은 계좌, 시장, 원천, 기준시각, 세 평가액, payload가 모두 같을 때만 멱등 성공한다. 하나라도 다르면 불변 스냅샷 충돌로 거부한다.

## 5. 원자적 위험 예약

`ai_risk_reservations`를 추가했다.

예약 소유 키:

```text
account_id
+ market
+ strategy_id
+ position_id
+ order_id
```

활성 상태에서 이 복합 키에 부분 유일 인덱스를 적용했다. 동일 주문/포지션 예약의 재시도는 기존 예약을 반환하며 새 예산을 소비하지 않는다. 같은 키로 다른 금액을 예약하려 하면 호출자 오류로 거부한다.

예약 금액:

- `cash_amount`: 주문을 위해 확보할 현금
- `risk_amount`: 손절 체결 시 예상 가능한 위험 금액

상태:

- `active`: 예산 합산에 포함
- `released`: 주문 취소 등으로 해제
- `consumed`: 체결·포지션 위험으로 전환
- `expired`: 유효시간 경과로 해제

### 5.1 트랜잭션 경계

`reserve_risk_budget()`은 `BEGIN IMMEDIATE` 안에서 다음을 수행한다.

1. 동일 활성 복합 키 조회
2. 동일 계좌·시장 전체의 활성 예약 현금과 위험 합산
3. 신규 예약을 더한 값이 `available_cash`와 `risk_budget_limit` 이내인지 검사
4. 통과한 경우에만 활성 예약 삽입
5. 커밋

쓰기 예약을 먼저 얻은 후 합산하므로 두 작업자가 동시에 같은 잔여 한도를 소비하는 check-then-insert 경쟁을 막는다.

위험 합산은 전략별이 아니라 동일 계좌·시장 전체를 기준으로 한다. 서로 다른 전략도 같은 계좌의 위험예산과 현금을 공유하므로 전략 경계를 이용해 한도를 우회할 수 없다.

### 5.2 해제

`release_risk_reservation()`은 활성 예약을 `released`, `consumed`, `expired` 중 하나로 원자 전환한다.

- 이미 종료된 예약의 재해제는 현재 상태를 그대로 반환한다.
- 존재하지 않는 예약은 거부한다.
- 종료된 예약은 활성 합산에서 제외되어 후속 주문이 예산을 사용할 수 있다.
- 이력 보존을 위해 행을 삭제하지 않는다.

## 6. 제공 API

시장 스냅샷:

- `create_market_snapshot(data)`
- `get_market_snapshot(snapshot_id)`
- `list_market_snapshots(market=None, limit=100)`

포트폴리오 스냅샷:

- `create_portfolio_snapshot(data)`
- `get_portfolio_snapshot(snapshot_id)`
- `list_portfolio_snapshots(account_id=None, market=None, limit=100)`

위험 예약:

- `reserve_risk_budget(data, available_cash, risk_budget_limit)`
- `get_risk_reservation(reservation_id)`
- `list_risk_reservations(...)`
- `release_risk_reservation(reservation_id, final_status, reason)`

## 8. 후속 연결 작업

이번 단계는 저장소 원자성을 제공하지만 아직 모든 주문 경로에 연결된 것은 아니다. 다음 단계에서 반드시 수행해야 한다.

1. 결정론적 위험 커널이 사용한 market/portfolio snapshot ID를 전략 결정에 연결
2. `RiskApprovedOrder` 생성 직전에 예약 생성
3. 승인 거절·주문 취소·만료·브로커 거절 시 `released`
4. 체결 시 예약을 `consumed`로 전환하고 실제 포지션 위험 원장에 반영
5. 부분체결 시 현금 예약 잔량 처리 정책 추가
6. 프로세스 재시작 시 만료된 활성 예약 회수
7. 모든 KR/US 주문 경로가 예약 ID 없이는 위험 증가 주문을 제출하지 못하도록 강제

특히 현재 API의 `available_cash`와 `risk_budget_limit`은 호출자가 제공한다. 다음 통합 단계에서는 반드시 동일 트랜잭션 또는 검증된 최신 포트폴리오 스냅샷에서 나온 값만 전달하도록 중앙 위험 커널에 캡슐화해야 한다. 임의 호출자가 큰 한도를 전달할 수 있는 상태로 브로커 주문 권한을 열어서는 안 된다.

## 9. 단계 결과

위험예산 이중사용을 막기 위한 DB 수준의 쓰기 직렬화, 계좌·시장 전체 합산 검사, 활성 키 멱등성, 비삭제 상태 이력이 마련됐다. 시장과 포트폴리오 판단 입력도 해시된 불변 레코드로 저장할 수 있다.

다만 이것만으로 “우회 불가능”이 완성된 것은 아니다. 중앙 위험 커널과 주문 상태 머신이 이 API를 필수 경로로 사용하도록 연결하고, 최종 단계에서 동시성·장애·재시작 테스트를 실행해 입증해야 한다.
