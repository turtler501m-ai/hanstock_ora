# 전략 구현 단계 0012: 최종 테스트 전 정적 통합 리뷰

## 범위와 제약

- 대상: `src/strategy/autonomy/` 및 연결 저장소·승인 서비스
- 추적 흐름: runtime → orchestrator → deterministic risk → approval → order → fill → protection
- 방법: 소스·호출부·데이터 계약만 정적으로 검토
- 이 단계에서는 요청에 따라 테스트, Python 실행, 배포를 수행하지 않았다.

## 흐름별 정적 판정

| 단계 | 구현 근거 | 판정 |
|---|---|---|
| runtime 입력 | `AutonomyRuntime.run`, `build_runtime_contexts` | 활성 정책, 신뢰 계좌/시장 스냅샷, 운영 모드를 fail-closed 검증한다. |
| AI 계획 | `AutonomousAIAdapter`, `TRADE_INTENT_JSON_SCHEMA` | AI는 수량을 만들 수 없고 완전한 `TradeIntent`를 구조화 출력한다. |
| 지속 판단 | `AutonomousStrategyOrchestrator.run_cycle` | 후보 스캔과 활성 전략 포지션 재평가를 같은 주기에 수행한다. |
| 결정론 위험 | `RiskEnvelope.evaluate` | 수량, 손실, 현금, 종목·시장·섹터·전략 비중, 유동성, 주문 수, 데이터 신선도, 보호 차단을 강제한다. |
| 위험 예약 | `reserve_risk_budget` | 주문 생성 전에 현금·위험·노출을 원자적으로 예약한다. |
| 승인 | `ManagedApprovalBridge` | 정식 주문과 승인 연결을 검증하고 최신 위험 스냅샷으로 다시 평가한다. |
| 실행 | `ManagedExecutionCoordinator`, `ManagedOrderService.submit` | 승인 서비스가 발행한 내부 capability 없이는 브로커 제출이 불가능하다. |
| 체결 | `ManagedOrderService.apply_fill`, `apply_managed_fill` | 체결을 전략 소유 가상 포지션에 원자적으로 귀속한다. |
| 보호 | `HardStopProtectionService` | 매수 체결 직후 전체 잔여 수량의 하드스톱 요청을 영속화하며 미보호 수량은 신규 위험을 차단한다. |
| 복구 | `ManagedOrderReconciler`, `AutonomousRecoveryService` | 재시작 시 미확정 주문과 하드스톱을 브로커 상태와 대조한다. |

## 이번 단계에서 수정한 명확한 결함

### 1. 전략 포지션별 청산 수량 강제

기존 `PortfolioContext`는 종목별 `RiskSnapshot.current_position_qty`만 제공했다.
운영 스냅샷의 이 값은 증권사 계좌 전체 종목 수량이므로, 동일 종목을 여러 전략이
소유한 경우 `REDUCE`/`EXIT`가 해당 전략의 가상 포지션보다 큰 수량을 승인할 수
있었다. 실제 체결 저장소가 초과 체결을 거절하더라도 주문 자체가 과대 제출되는
결함이었다.

수정:

- `PortfolioContext.position_quantities`에 `position_id → remaining_qty`를 보관한다.
- `risk_snapshot_for(symbol, position_id)`가 포지션 소유 수량으로 복제한 위험
  스냅샷을 반환한다.
- 오케스트레이터는 `ADD`, `REDUCE`, `EXIT`에서 반드시 `position_id`별
  스냅샷을 요구한다.
- 운영 runtime은 활성 전략 포지션에서 이 매핑을 구성한다.
- 매핑이 없으면 추측하지 않고 `missing trusted risk snapshot`으로 거절한다.

### 2. `SUBMITTING` 취소 상태 전이 복구

`ManagedOrderService.cancel`은 `SUBMITTING`을 브로커 취소 대상에 포함했지만,
상태표에는 `SUBMITTING → CANCEL_PENDING`이 없었고 후속 전이의 기대 상태에서도
`SUBMITTING`이 누락되어 있었다. 따라서 해당 경로는 항상 상태 오류로 끝났다.

수정:

- 허용 전이에 `SUBMITTING → CANCEL_PENDING`을 추가했다.
- 브로커 취소 후 후속 전이가 `CANCEL_PENDING`을 기대하도록 조건을 맞췄다.

### 3. runtime·continuous 승인 계획 연결

`ManagedApprovalPlanService`를 추가해 오케스트레이터 결과와 `RuntimeResult`의
위험 승인 주문을 `ManagedApprovalBridge.queue`까지 명시적으로 진행한다.

- `queue_cycle`은 `INTENT_CREATED` 주문을 먼저 `RISK_APPROVED`로 이동한 뒤 승인
  큐에 등록한다.
- 중간 실패 후 다음 주기에 오케스트레이터가 `duplicate`를 반환해도 기존 주문을
  재조회해 이어서 처리한다.
- 이미 `APPROVAL_QUEUED`인 주문은 canonical `approval_id`를 반환하므로 재호출이
  중복 승인을 만들지 않는다.
- `queue_runtime_result`는 기존 runtime이 반환한 risk-approved 주문을 같은 승인
  계획 경계로 연결한다.
- `ContinuousStrategyService`는 `ApprovalPlanQueue`를 필수 의존성으로 받고 각
  전략 cycle 직후 승인 계획을 수행한다.
- 이 서비스에는 approve나 execute 기능이 없다. 자동 승인·브로커 실행은 정책
  검증과 별도 coordinator를 거쳐야 한다.

### 4. 전략 버전 타입 통일

전략 저장소와 승인 DB의 `strategy_version INTEGER` 계약에 맞춰 자율 운영 도메인도
양의 정수 하나로 통일했다.

- `TradeIntent.strategy_version`: `int`
- AI JSON Schema: 최소 1의 `integer`
- `AutonomousAIAdapter`: 정수 버전
- lifecycle/intent validation: bool을 제외한 양의 정수 강제
- runtime: 등록 전략의 정수 버전 사용
- `ApprovalCreateRequest`/`ApprovalRecord`: 기존 정수 계약을 그대로 사용
- 승인 재검증: 문자열 변환 비교 없이 정수 동일성 검사

## 계약·시그니처 검토 결과

- `StrategyAdapter.scan/manage_position`과 `AutonomousAIAdapter` 구현 시그니처가 일치한다.
- `FreshRiskSnapshotProvider.snapshot_for_approval`은 예약 자기중복을 제외할
  `exclude_position_reservation_id`를 필수로 전달한다.
- `BrokerGateway`와 KR/US 어댑터의 submit/cancel 반환 계약이 일치한다.
- `ProtectionBroker`의 submit/amend/cancel/fetch/position-qty 계약은 보호·복구
  서비스 호출과 일치한다.
- `TradeIntent.to_dict`와 `trade_intent_from_payload`의 필수 필드가 상호 대응한다.
- 패키지 `__init__.py`는 주요 runtime, risk, approval, order, protection,
  reconciliation 공개 타입을 내보낸다.

## 최종 테스트 전에 남은 통합 위험

아래 항목은 정적 검토만으로 완성됐다고 판정할 수 없으며 최종 단계에서 반드시
검증하거나 추가 조립해야 한다.

1. `OperationalSnapshotProvider._account_payload`는
   `strategy_exposure_value`와
   `open_position_risk_amount_excluding_reservations`를 항상 `0.0`으로 만든다.
   실운영 스냅샷에서 기존 전략 노출·열린 위험을 저장소로부터 산출하지 않으면
   전략 비중과 총 열린 위험 한도가 보수적으로 강제되지 않는다.
2. 실운영 계좌 컨텍스트는 킬 스위치를 항상 `False`로 기록한다. 파일 또는 운영
   상태의 실제 킬 스위치 공급자가 연결되어야 한다.
3. 보호 브로커가 없는 `ManagedOrderService`도 매수 체결을 기록하고 보호 요청만
   영속화한다. 이는 이후 전역 차단으로 fail-closed 되지만, “체결 즉시 활성
   보호주문”을 보장하려면 실제 실행 조립에서 `protection_broker` 필수 주입을
   검증해야 한다.
위 세 항목은 전체 자율 운영 완료 판정의 선행 조건이다.
정적 리뷰 단계에서는 숨기지 않고 미완성 통합 항목으로 유지한다.

## 최종 검증 체크리스트

최종 테스트 단계에서는 최소한 다음을 증명해야 한다.

- 동일 종목을 여러 전략·여러 포지션이 보유해도 각 청산 주문이 소유 수량을
  초과하지 않는다.
- runtime에서 생성된 주문이 risk-approved → approval-queued → approved →
  submitting → submitted → partial/filled로 이어진다.
- 매수 부분체결 직후 보호 요청이 생성되고, 실제 보호 실패 동안 신규 위험이
  차단된다.
- 매도 부분체결 때 하드스톱 수량이 잔여 전략 수량으로 축소되고 전량 청산 시
  취소된다.
- 재시작 후 broker-unknown, 부분체결, 취소 대기 주문이 중복 제출 없이 복구된다.
- 기존 포지션 위험·전략 노출·킬 스위치가 실제 운영 스냅샷에 반영된다.
- 승인 시 최초 위험 수량보다 최신 허용 수량이 작아지면 주문이 거절된다.
- AI/스냅샷/저장소/브로커 예외가 규칙 전략 또는 임의 수량으로 fallback하지 않는다.
