# K02. 전략 구현 단계 0001 — 현행 아키텍처 감사

작성일: 2026-07-23  
범위: AI 판단, 전략 실행, 위험 통제, 주문·승인, 체결·DB 구조의 정적 감사  
단계 제약: 이 단계에서는 애플리케이션 코드를 수정하지 않았고 테스트·배포도 수행하지 않았다.

## 1. 목표와 완료 판정 기준

최종 목표는 다음 문장으로 고정한다.

> AI가 시장과 포지션을 지속적으로 판단하고 완전한 거래 계획을 생성하되, 수량·손실·비중·주문 안전은 절대 우회할 수 없는 결정론적 엔진이 통제하는 자율 전략 플랫폼

이 목표가 완료되었다고 판정하려면 아래 요구사항을 모두 권위 있는 실행 증거로 입증해야 한다.

1. AI는 시장 국면과 신규 후보뿐 아니라 모든 활성 전략 포지션을 반복 평가한다.
2. AI 또는 규칙 전략의 출력은 진입·추가·유지·축소·청산·취소를 표현하는 하나의 검증된 거래 의도 스키마를 따른다.
3. 거래 의도에는 전략·모델·프롬프트 버전, 판단 시각과 데이터 시각, 논리, 무효화 조건, 가격 범위, 손절, 목표/추적 손절, 유효기간, 최대 보유기간이 포함된다.
4. 증권사 보유 수량과 별도로 전략별 가상 포지션을 보존하며, 포지션을 연 전략만 자신의 가상 수량을 관리한다.
5. 최종 주문 수량은 AI가 아니라 결정론적 위험 엔진이 계산한다.
6. 거래당 위험, 일일 손실, 종목·전략·시장·섹터 비중, 현금, 유동성, 중복 주문, 데이터 신선도, 시장 상태, 킬 스위치를 중앙 게이트가 강제한다.
7. 안전 검사가 실패하거나 검사 자체가 예외·타임아웃·미확정 상태이면 신규 위험 주문은 거부되는 fail-closed 방식이다.
8. 하드 스톱은 진입 체결 후 반드시 활성화되고, 손실 확대 방향 변경이나 AI 취소가 불가능하다.
9. 주문은 의도 생성부터 위험 승인, 제출, 부분체결, 체결, 보호 활성화, 청산까지 지속 가능한 상태 머신으로 관리된다.
10. 프로세스 재시작 후 상태 복구와 증권사 주문·잔고 대사가 가능하고, 중복 제출은 멱등 키로 차단된다.
11. AI 제안, 위험 엔진 결정, 주문 요청, 증권사 결과, 체결, 포지션 변화가 서로 연결된 감사 로그로 재현된다.
12. 전략은 검증·백테스트·모의·제한 실거래·실거래의 명시적 생명주기를 따르고 승인되지 않은 버전은 주문할 수 없다.
13. AI 호출 실패 시 다른 규칙 전략으로 암묵 전환하지 않으며, 명시적으로 승인된 대체 정책만 사용할 수 있다.
14. KR/US 등 시장별 브로커 차이는 어댑터 아래에 격리되고 동일한 핵심 위험 불변조건을 적용받는다.
15. 최종 단계에서 단위·통합·장애주입·재시작·모의 체결 검증이 위 불변조건 전체를 직접 입증한다.

## 2. 감사 방법과 권위 증거

이번 감사는 현재 작업 트리의 소스와 스키마를 권위 증거로 삼았다. 문서나 과거 분석의 설명만으로 구현 여부를 판정하지 않았다.

| 영역 | 권위 증거 |
|---|---|
| 전역 거래 안전 기본값 | `src/config.py`의 `Settings`, `trading_flags()` |
| 기존 주식 실행 흐름 | `src/trader.py`의 `build_runtime_plan()`, `run()`, `execute_plan_row()` |
| 기존 후보·보유 신호 | `src/strategy/seven_split.py`의 `calc_strategy_profile()`, `find_candidates()`, `build_orders()`, `generate_signal()` |
| AI 후보 점수 | `src/strategy/predict.py`의 `ModelPredictor` |
| AI 종목 자동화 | `src/ai_stock/automation_service.py`의 `evaluate_gate()`, `run_strategy()` |
| AI 실행 계획·수량 | `src/ai_stock/execution_plan_service.py`의 `create_plan()` |
| 주문 경로 | `src/strategy/router.py`의 `OrderRouter.route()` 및 `src/execution_service.py` |

| 전략 생명주기 | `src/db/strategy_repository.py` |

이 단계에서는 테스트를 실행하지 않았으므로, 아래의 “존재” 판정은 정적 코드 증거일 뿐 실제 동작 보증이 아니다.

## 3. 현행 구조

### 3.1 현재 실행 경로는 하나가 아니다

현행에는 최소 세 개의 겹치는 실행 경로가 있다.

1. `src/trader.py`의 전통 주식 실행 경로
   - 보유 종목 신호와 신규 후보를 실행 계획 행으로 합친다.
   - 일일 손실 중단, 승인, `OrderRouter`를 거쳐 주문한다.
2. `src/ai_stock/automation_service.py`의 AI 종목 자동화 경로
   - 스캔 → 관심종목 → 확인 → 실행 계획 → 승인 → 실행 순으로 진행한다.
   - 시장에 따라 KR 주문 라우터 또는 US 전용 경로로 분기한다.
3. `src/mistock/`의 미국 주식 경로
   - 승인 DB와 실제 실행 방식 일부가 KR 경로와 별개다.

각 경로가 동일한 중앙 위험 게이트를 반드시 통과한다는 구조적 보장은 없다. 안전 규칙을 개별 호출자가 올바르게 조합해야 하므로 새 경로가 규칙을 누락할 위험이 있다.

### 3.2 AI의 현재 권한

`src/strategy/predict.py`의 `ModelPredictor`는 기술 특성을 OpenAI에 보내 `probability`와 `rationale`만 요구한다. 실제 반환 활용은 후보 점수 혼합이다.

- 규칙 점수와 확률 환산 점수를 혼합한다.
- 신뢰도 미달이면 규칙 점수로 복귀한다.
- API 키 부재, 호출 예외도 규칙 점수 기반 fallback 상태가 된다.
- AI는 진입 가격 범위, 손절, 목표, 보유기간, 청산, 주문 취소를 결정하지 않는다.
- 반환된 `rationale`은 `_predict_probability()`에서 파싱되지만 호출자 결과에는 보존되지 않는다.

별도의 `src/ai_stock/` 계층은 스캔 후보와 실행 계획을 제공하지만, `run_strategy()`가 자동 생성하는 손절가는 현재가의 95%라는 고정 참고값이다. 이는 AI가 완전한 거래 논리를 생성한 결과가 아니다.

### 3.3 전략의 현재 책임 범위

`src/strategy/seven_split.py`는 후보 평가, AI 점수 혼합, 변동성 기반 신규 배분, 기존 보유 신호를 한 모듈에 결합한다. 커스텀 전략은 주로 `calculate_score()`로 진입 후보 점수에 참여한다.

보유 포지션 신호는 공통 `generate_signal()` 규칙을 중심으로 처리된다. DB에 “이 수량을 어느 전략이 어떤 논리로 열었는지”를 나타내는 전략 포지션 원장이 없으므로, 진입 전략이 청산까지 소유한다는 원칙을 구현할 수 없다.

### 3.4 현재 실행 계획

두 종류의 계획 표현이 존재한다.

- `src/execution_plan.py`의 `PlanRow`: 화면/런타임 실행 행에 가까운 범용 표현
- `ai_stock_execution_plans`: AI 후보의 매수 계획 저장

`ai_stock_execution_plans`는 `action`, 단일 `entry_price`, `stop_price`, 단일 `take_profit`, `risk_budget`, `quantity`, `safety_checks`, 승인 참조를 가진다. 그러나 현재 생성기는 `action="buy"`만 만든다.

다음은 표현하거나 강제할 수 없다.

- 진입 가격 범위와 주문 유효기간
- 유지·추가·부분축소·전량청산·미체결 취소
- 다단계 목표가와 각 축소 비율
- 추적손절 규칙
- 논리 무효화 조건
- 최대 보유기간
- 원 거래 의도와 위험 엔진 수정 결과의 분리
- 포지션 및 주문 상태 버전

### 3.5 현재 수량·비중 통제

`src/ai_stock/execution_plan_service.py`에는 의미 있는 기반이 존재한다.

```text
위험 예산 = total_capital × max_risk_per_trade_pct
위험 기준 수량 = floor(위험 예산 / (진입가 - 손절가))
최종 수량 = min(위험 기준, 자금 기준, 포트폴리오 기준)
```

계좌 스냅샷이 사용 가능하면 현금, 단일 종목 비중, 시장 노출도도 검사한다. 그러나:

- `qty_by_cash`가 실제 현금이 아니라 설정된 `total_capital`을 기준으로 먼저 계산된다.
- 계좌 스냅샷을 얻지 못하면 포트폴리오 수량 상한은 사실상 무한대로 반환된다.
- 계좌 스냅샷 불가 검사는 `unavailable_nonblocking`으로 통과한다.
- 전략별·섹터별·상관관계별·일일 신규 위험 총량 제한이 없다.
- 열린 포지션의 손절 위험을 합산한 계좌 위험 원장이 없다.

따라서 현재 계산은 좋은 출발점이지만 “절대 우회할 수 없는” 포트폴리오 위험 엔진은 아니다.

### 3.6 현재 주문·승인·체결

`OrderRouter.route()`는 DRY_RUN, 승인 필요, 실제 제출로 분기하고 거래를 저장한다. 실제 제출 직후의 상태는 `submitted`, 체결 수량은 0으로 기록된다.

`trades`에는 `broker_order_id`, `order_status`, `filled_qty`, `filled_price`, `pre_order_qty`가 있어 체결 기록의 기초는 있다. 하지만 감사한 실행 경로에는 다음을 책임지는 지속 주문 관리자가 없다.

- 브로커 주문 상태 반복 조회
- 부분체결 누적과 잔량 정정·취소
- 제출 타임아웃 뒤 미확정 상태 보존
- 클라이언트 멱등 키
- 재시작 후 미종결 주문 복원
- 내부 주문과 증권사 주문/잔고 대사
- 진입 체결 직후 보호 손절 활성화 확인

또한 AI 자동화 실행 성공은 반환값의 `ok` 또는 `executed/submitted` 상태만으로 판단한다. `submitted`는 체결이나 보호 활성화를 의미하지 않는데 실행 run은 `completed`로 기록될 수 있다.

### 3.7 현재 전략 생명주기와 감사성

전략 저장소에는 프로필, 해시, 버전, 상태, 검증·백테스트·paper 시각과 이벤트 기록이 존재한다. 자동 승인/실행 게이트는 승인 상태, 프로필 해시, 전략 버전을 일부 확인한다.

다만 후보에 기대 해시가 없으면 해시 비교가 생략되고, 기대 버전이 없으면 버전 비교도 생략된다. “승인된 정확한 버전만 주문”이라는 강한 불변조건에는 부족하다.

AI 스캔·후보·관찰·실행 계획·실행 run 테이블도 존재한다. 그러나 AI 원시 입력/응답, 프롬프트 버전, 모델 호출 ID, 위험 엔진 전후 의도, 포지션 변화, 체결 이벤트를 하나의 결정 ID로 잇는 완전한 감사 사슬은 없다.

## 4. 안전 불변조건 감사

아래 불변조건은 구현 과정에서 기능 편의를 위해 완화해서는 안 된다.

| ID | 불변조건 | 현행 판정 | 근거와 격차 |
|---|---|---|---|
| S-01 | 모든 주문은 중앙 결정론적 위험 게이트를 통과한다 | 미충족 | 실행 경로가 여러 개이고 공통 강제 진입점이 없다. |
| S-02 | 안전 검사 오류·불가·미확정은 신규 위험을 차단한다 | 위배 | `_kill_switch_active()` 예외는 `False`, 계좌 스냅샷 불가는 비차단이다. |
| S-03 | AI는 주문 수량을 확정할 수 없다 | 부분 충족 | AI 실행 계획 수량은 결정론적으로 계산되나 다른 기존 경로는 별도 배분기를 쓴다. |
| S-04 | 실제 현금과 포트폴리오 노출을 확인하지 못하면 신규 매수를 차단한다 | 위배 | 계좌 스냅샷 불가 시 `10**12` 수량 상한과 비차단 검사를 사용한다. |
| S-05 | 손절 없는 신규 포지션은 없다 | 부분 충족 | AI 계획 생성에는 양의 손절거리가 필요하지만 기존 주문 전체와 체결 후 보호 활성화에는 강제되지 않는다. |
| S-06 | 하드 스톱은 손실 확대 방향으로 이동·취소할 수 없다 | 미구현 | 지속 포지션/보호주문 모델이 없다. |
| S-07 | 일일 손실 한도는 모든 신규 위험 경로에 동일 적용된다 | 미충족 | `trader.py`와 `RiskEngine`에는 있으나 AI 자동화 게이트의 `max_daily_loss_pct`는 실제 평가되지 않는다. 정책 컬럼만 존재한다. |
| S-08 | 일일 주문 수는 실제 주문/체결의 권위 원장으로 계산된다 | 미충족 | 실행 run 중 `completed`와 candidate가 있는 건수를 센다. 제출/실패/부분체결 의미와 불일치 가능하다. |
| S-09 | 승인된 정확한 전략 버전과 해시만 주문한다 | 부분 충족 | 후보 필드가 비어 있으면 비교가 생략된다. |
| S-10 | 중복 주문을 원자적 멱등 키로 차단한다 | 미구현 | 동일 candidate의 활성 계획을 목록 조회로 검사할 뿐 DB 유일 제약·주문 멱등 키가 없다. |
| S-11 | 매도 수량은 해당 전략 소유 잔량과 실제 보유량을 모두 넘지 않는다 | 미구현 | 전략 포지션 원장이 없다. |
| S-12 | AI 실패는 암묵적 매매 전략 전환을 유발하지 않는다 | 위배 가능 | `ModelPredictor`는 규칙 점수로 fallback한다. 정책이 막을 수 있는 별도 후보 경로도 있으나 전체 시스템에 일관되지 않다. |
| S-13 | 오래된 데이터 거래는 원칙적으로 차단한다 | 부분 충족 | 정책으로 stale 거래 허용이 가능하다. 안전 핵심 입력별 신선도와 주문 직전 재검증이 없다. |
| S-14 | 제출 성공과 체결 성공, 보호 활성화는 별도 상태다 | 위배 | AI 자동화가 `submitted`를 성공으로 보고 run을 `completed` 처리할 수 있다. |
| S-15 | 킬 스위치는 모든 위험 증가 행동을 차단한다 | 부분 충족 | 기존 코드는 주로 `buy`를 차단하며 중앙 경로 보장이 없다. |
| S-16 | 위험 감소 매도는 신규 매수 제한 때문에 막히지 않는다 | 검증 불가 | 통합 의도/게이트가 없고 경로별 의미가 다르다. |

## 5. 데이터 모델 격차

### 5.1 반드시 추가할 핵심 엔터티

#### `strategy_positions`

실제 브로커 보유와 전략별 가상 소유권을 연결한다.

필수 필드:

- `position_id`, `account_id`, `market`, `symbol`
- `strategy_id`, `strategy_version`, `profile_hash`
- `status`, `opened_at`, `closed_at`
- `entry_thesis`, `invalidation_json`
- `average_price`, `filled_qty`, `remaining_qty`
- `initial_stop_price`, `current_stop_price`
- `target_plan_json`, `trailing_stop_json`, `max_holding_until`
- `initial_risk_amount`, `current_risk_amount`
- `realized_pnl`, `unrealized_pnl`
- `row_version`, `last_decision_id`, `last_evaluated_at`

#### `trade_intents` 또는 `strategy_decisions`

AI/규칙 전략의 원래 제안과 검증 결과를 불변 기록한다.

필수 필드:

- 결정 ID와 부모 결정 ID
- 전략·모델·프롬프트·특성 버전 및 해시
- 포지션 ID, 시장, 종목, 액션
- 판단 시각과 모든 입력 데이터의 `as_of`
- 진입 범위, 무효화, 손절, 목표, 추적손절, 유효기간
- 신뢰도, 논리, 원시 구조화 응답
- 위험 게이트 결과, 수정/거절 이유, 최종 허용 액션

#### `orders`와 `order_events`

현재 `trades` 한 행에 섞인 주문 요청·상태·체결을 이벤트 기반으로 분리한다.

- 내부 주문 ID와 고유 `client_order_key`
- intent/position/plan 연결
- 요청 수량·가격, 누적 체결, 잔량
- `created`, `risk_approved`, `approval_queued`, `submitted`, `partially_filled`, `filled`, `cancel_pending`, `canceled`, `rejected`, `broker_unknown`
- 브로커 원문 응답과 각 상태 이벤트

#### `fills`와 `position_ledger`

부분체결을 불변 원장으로 저장하고 전략 가상 포지션 수량 변화를 파생한다.

#### `risk_reservations`

계획 생성과 체결 사이의 동시 주문이 같은 현금·위험 한도를 중복 사용하는 일을 막는다. 계획 승인 시 위험과 현금을 원자적으로 예약하고 만료·취소·체결 시 해제/전환해야 한다.

#### `market_snapshots`와 `portfolio_snapshots`

판단에 사용한 입력을 재현할 수 있도록 데이터 시각, 원천, 신선도, 계좌·포지션·미체결 노출을 저장한다.

### 5.2 기존 테이블의 활용 가능성

- `ai_strategies`, `ai_strategy_events`: 전략 레지스트리와 생명주기 기반으로 유지 가능
- `ai_stock_scans`, `ai_stock_candidates`: 탐색 및 후보 감사 기록으로 유지 가능
- `ai_stock_watchlist`, `ai_stock_watch_events`: 진입 전 관찰 상태로 유지 가능
- `ai_stock_execution_plans`: 신규 스키마 이행 기간의 호환 뷰 또는 폐기 후보
- `ai_stock_execution_runs`: 오케스트레이션 실행 요약으로 유지하되 주문의 권위 원장으로 사용하면 안 됨
- `trades`: 성과용 거래 요약으로 유지 가능하지만 주문·체결 권위 원장 역할은 새 엔터티로 분리해야 함
- `approvals`: 사용자 승인 기록으로 유지하되 승인 대상의 불변 plan/intent 버전과 해시 연결이 필요

## 6. 목표 아키텍처 경계

```text
Market/Account Data Adapters
        ↓  (timestamped snapshots)
Strategy Runtime
  - market regime
  - candidate scan
  - position re-evaluation
        ↓  (validated TradeIntent)
Deterministic Risk Kernel
  - invariant checks
  - quantity calculation
  - risk reservation
        ↓  (RiskApprovedOrder)
Approval Policy
        ↓
Order Manager
  - idempotent submit/amend/cancel
  - poll/reconcile/recover
        ↓
Broker Adapters (KR/US)
        ↓
Fill & Position Ledger
        ↺ Strategy Runtime
```

의존 방향은 단방향이어야 한다.

- 전략은 브로커를 직접 호출하지 않는다.
- AI는 `TradeIntent`만 생성한다.
- 위험 커널만 최종 주문 수량을 생성할 수 있다.
- 승인 서비스는 위험 검사를 우회하지 않고 이미 위험 승인된 불변 주문 요청에 사람의 권한만 더한다.
- 주문 관리자는 전략 판단을 바꾸지 않는다.
- 브로커 어댑터는 정책을 판단하지 않는다.
- 체결/포지션 원장이 보유 수량과 위험의 권위 원천이다.

## 7. 우선순위별 구현 계획

테스트는 사용자 지시에 따라 최종 검증 단계에서 일괄 수행한다. 단, 각 구현 단계에서는 정적 자체 점검과 문서 결과를 남겨 다음 단계가 이전 단계의 계약을 건너뛰지 않게 한다.

### P0-1. 공통 도메인 계약

산출물:

- 액션 enum과 `TradeIntent`
- 진입·손절·목표·추적·유효기간 스키마
- 데이터 신선도 및 전략/모델 버전 필수 필드
- 구조 검증 실패 시 거래 금지

완료 증거:

- 모든 전략 출력이 같은 계약으로 변환됨
- 잘못된/누락된 의도는 주문 계층 타입으로 변환 불가

### P0-2. 전략 포지션·결정·원장 DB

산출물:

- 전략 가상 포지션, 결정 로그, 주문 이벤트, 체결, 포지션 원장, 위험 예약 스키마
- 원자적 생성/갱신과 낙관적 버전 잠금
- 기존 DB 마이그레이션

완료 증거:

- 한 종목의 여러 전략 수량을 독립 추적
- 모든 수량 변화가 fill/ledger로 설명됨
- 전략 잔량 합이 실제 잔고를 초과하면 대사 오류 상태

### P0-3. 중앙 결정론적 위험 커널

산출물:

- 모든 주문 경로가 호출해야만 브로커 제출 타입을 얻는 단일 게이트
- 거래당·일일·종목·전략·시장·섹터 위험과 실제 현금 강제
- 킬 스위치, 신선도, 시장상태, 중복, 유동성 검사
- 검사 오류 시 fail-closed
- 위험 감소 주문과 위험 증가 주문의 명확한 분리

완료 증거:

- 브로커 어댑터가 서명/토큰화된 `RiskApprovedOrder` 외 입력을 받지 않음
- 계좌 조회/킬 스위치/정책 조회 오류 시 매수 불가
- AI 제공 수량이 최종 주문 수량에 직접 사용되지 않음

### P0-4. 주문·체결 상태 머신과 대사

산출물:

- 멱등 주문 제출
- 부분체결, 정정, 취소, 만료, 브로커 미확정 상태
- 재시작 복구
- 브로커 주문/잔고 대사
- 체결 후 보호 손절 활성화 상태

완료 증거:

- `submitted`가 `filled`나 `completed`로 오인되지 않음
- 동일 멱등 키 재호출이 중복 주문을 만들지 않음
- 재시작 뒤 미종결 주문과 포지션을 복원

### P1-1. 지속 전략 런타임

산출물:

- 시장 국면 평가 루프
- 신규 후보 루프
- 모든 활성 포지션 재평가 루프
- 이벤트와 주기 실행을 함께 지원
- 이전 논리와 결정 이력을 AI 입력에 포함

완료 증거:

- 진입한 전략이 자신의 포지션에 HOLD/ADD/REDUCE/EXIT/CANCEL을 생성
- 최대 보유기간·무효화·목표·추적손절 작동

### P1-2. 하드 스톱·목표·추가매수 정책

산출물:

- 체결 수량에 대응하는 보호 상태
- 손절 완화 금지
- 사전 계획된 추가매수만 허용
- 추가 후에도 총 위험 예산 유지

완료 증거:

- 보호되지 않은 체결 수량이 0이 아니면 경보/위험 감소 조치
- 손절가를 손실 확대 방향으로 바꾸는 의도 거부

### P1-3. 기존 KR/US 경로 통합

산출물:

- `trader.py`, AI 자동화, 미스톡 경로가 공통 위험·주문 관리자 사용
- 시장별 브로커 동작만 어댑터로 격리
- 기존 라우터 직접 호출 제거 또는 내부 전용화

완료 증거:

- 저장소 검색으로 위험 커널 밖의 실제 브로커 제출 경로가 없음
- KR/US가 같은 주문 상태와 안전 불변조건을 가짐

### P2-1. 전략 생명주기와 자동 중단

산출물:

- 상태 전이 규칙과 승인된 정확한 버전 고정
- 성과·오류·대사 불일치 기반 자동 `review_required/suspended`
- 명시적 fallback 승인 정책

완료 증거:

- 미승인/해시 불일치/버전 누락 전략 주문 불가
- 모델 실패가 암묵적 규칙 거래로 전환되지 않음

### P2-2. 관측성·감사·운영 복구

산출물:

- 결정 ID 중심 추적
- AI 입력/응답, 위험 판단, 승인, 주문, 체결, 포지션 연결
- 보호 누락·오래된 데이터·대사 오류·미확정 주문 경보
- 운영자용 정지/재개와 사유 감사

완료 증거:

- 임의 거래를 단일 결정 ID에서 입력부터 손익까지 재현

## 9. 즉시 해결해야 할 핵심 결함

우선순위가 가장 높은 결함은 다음과 같다.

1. 킬 스위치 검사 예외가 비활성으로 처리되는 fail-open 동작
2. 계좌 스냅샷 불가가 포지션 제한 비차단으로 처리되는 동작
3. 정책에 존재하는 `max_daily_loss_pct`가 AI 자동 실행 게이트에서 사용되지 않는 점
4. `submitted` 주문을 완료 실행으로 기록할 수 있는 상태 의미 혼용
5. 전략별 포지션 소유권과 체결 원장이 없는 점
6. 중앙 위험 게이트 밖의 복수 주문 경로
7. DB 원자성 없는 목록 조회 기반 중복 계획 검사
8. 후보 버전/프로필 해시 누락 시 검사를 생략하는 점
9. 자동 생성 손절이 전략 논리가 아닌 현재가 대비 고정 5%인 점
10. AI 판단 실패가 규칙 점수로 암묵 복귀할 수 있는 점

이 결함들은 AI 기능 확대보다 먼저 또는 동시에 해소해야 한다. AI가 더 많은 액션을 만들도록 먼저 확장하면 기존 fail-open 경로와 상태 불명확성이 주문 위험을 확대한다.

## 10. 1단계 결론

현행 한스톡에는 후보 스캔, 전략 버전, 승인, DRY_RUN/실거래 게이트, 손절거리 기반 수량 계산, 포트폴리오 비중 검사, 실행 로그 등 재사용 가치가 높은 기반이 있다.

그러나 목표 플랫폼의 핵심인 “지속 포지션 판단”과 “절대 우회 불가능한 결정론적 통제”는 아직 성립하지 않는다. 구조적 원인은 공통 거래 의도 부재, 전략 포지션 원장 부재, 중앙 위험 커널 부재, 주문 상태 머신 부재이며, 현행 일부 안전 검사는 명시적으로 fail-open이다.

따라서 후속 구현은 `공통 도메인 계약 → 전략/결정/체결 원장 → 중앙 위험 커널 → 주문 상태 머신 → 지속 전략 런타임 → 기존 경로 통합 → 생명주기/감사 → 최종 검증` 순서를 유지한다. 이 순서는 기능 목록이 아니라 안전 의존관계이며 중간 단계를 건너뛰지 않는다.
